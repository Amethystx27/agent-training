# 实验1：会议通知智能信息提取实验总结

## 一、实验目的

本实验使用大语言模型从会议通知中提取结构化信息，并通过程序检查模型输出是否满足字段、日期、费用和 JSON 格式要求。实验的主要目标包括：

- 掌握会议名称、日期、地点、主题、投稿截止日期、注册费用和主办方等字段的提取方法。
- 学习使用 Prompt 约束模型输出。
- 使用 Pydantic 对 JSON 进行字段、类型和业务规则校验。
- 比较基础 Prompt 与改进 Prompt 对输出稳定性的影响。

## 二、运行环境

- 操作系统：Windows 10.0.26200。
- 执行日期：2026-11-13。
- Python：3.12.10。
- 依赖：`openai 3.46.0`、`python-dotenv 1.2.4`、`pydantic 2.14.3`。
- 模型接口：通过 `OPENAI_BASE_URL` 和 `MODEL_NAME` 配置的 OpenAI 兼容接口。
- 生成参数：`temperature=0.1`，单次请求超时 60 秒。
- 安全约束：API Key 仅从环境变量读取，没有写入代码、README、结果文件或截图。

程序优先读取实验目录内的 `.env`，如果不存在则读取上一级项目目录中的 `.env`。

## 三、测试输入

实验使用三份具有不同难点的会议通知：

| 输入 | 内容特点 | 主要测试目标 |
|---|---|---|
| `data/notice_a.txt` | ICCBDA 2027 信息完整，包含会议日期、多个重要日期、主题和三类注册费用 | 完整字段提取、日期格式规整、多个费用类别 |
| `data/notice_b.txt` | Edge Intelligence Forum 2027 只提供城市、月份和主题，截止日期与费用未公布 | 缺失值处理，检查模型是否编造日期、费用或主办方 |
| `data/notice_c.txt` | Smart Networks 2027 同时包含摘要注册、全文投稿、录用通知和早鸟注册日期 | 多日期分类，避免把不同截止日期放入同一字段 |

## 四、Prompt 设计

### Prompt V1：基础版

V1 使用较简洁的字段说明和基础规则，要求模型：

- 返回包含十个指定字段的 JSON。
- 未知信息使用 `null`。
- 日期使用 `YYYY-MM-DD`。
- 只把明确的全文投稿日期放入 `submission_deadline`。
- 将费用保存为包含类别、金额和币种的数组。

### Prompt V2：改进版

V2 在 V1 基础上进一步明确：

- 每个字段的业务含义和空值规则。
- 会议起止日期与摘要注册、录用通知、最终论文提交、早鸟注册日期的分类方式。
- `other_dates` 和 `registration_fee` 的限定结构。
- 不允许增加额外字段。
- 费用金额必须是正数，币种使用三位大写字母代码。
- `supported by`、`sponsored by`、联系人或秘书处不能被直接认定为主办方。
- 会议单日举办时允许开始日期与结束日期相同。

V2 通过更具体的字段定义和业务规则减少模型自行分类造成的不一致，但仍要求模型在原文没有依据时输出 `null`。

### 进阶 AIIoT 任务结果

AIIoT 2027 进阶任务使用 `data/notice_d.txt` 和独立的数据模型。最终保存的两版结果均通过严格校验：

## 六、结果分析

### 1. 通知 A

两个 Prompt 均正确提取了会议起止日期、投稿截止日期、五个主题、三项注册费用和主办单位。

V1 的 `conference_full_name` 为：

```text
The 11th International Conference on Cloud Computing and Big Data Analytics (ICCBDA 2027)
```

V2 的对应结果为：

```text
The 11th International Conference on Cloud Computing and Big Data Analytics
```

V2 将会议简称从完整名称中分离得更清楚，与实验文档中的参考输出更一致。

### 2. 通知 B

两个 Prompt 都将以下未知信息保留为 `null`：

- `start_date`
- `end_date`
- `submission_deadline`
- `organizer`

模型没有根据“Chengdu, China”和“October 2027”猜测具体会议日期，也没有把支持单位误写为主办方。

V1 将 `registration_fee` 输出为 `null`，V2 输出为空数组 `[]`；两者都能表达没有收费信息。`other_dates` 也输出为空数组，表示没有其他明确日期。

### 3. 通知 C

两个 Prompt 均正确提取：

- 全文投稿截止日期：`2027-07-24`
- 摘要注册截止日期：`2027-07-10`
- 录用通知日期：`2027-09-05`
- 早鸟注册截止日期：`2027-10-01`

费用方面，两个 Prompt 均正确识别学生 SGD 300、普通参会者 SGD 480。V1 将类别写成 `regular`，V2 使用更贴近原文的 `regular participants`。

## 七、错误和差异分析

本次六次运行没有出现 JSON 解析错误、字段缺失、无效日期、费用字符串或额外字段错误。因此，在当前小样本测试中，V1 和 V2 的 JSON 合法率、运行成功率和字段存在率均为 100%。

两版 Prompt 的差异主要出现在语义层面：

- V1 的会议完整名称可能包含括号中的会议简称，V2 对简称和完整名称的区分更清晰。
- V1 对收费类别的表述较为概括，V2 更倾向于保留原文中的人群描述。
- 对于完全没有信息的情况，空数组和 `null` 都可能通过结构校验，但二者表达的含义略有差异。

这些问题说明，JSON 合法和字段存在只能说明结构正确，不能证明所有字段的语义都正确。若要计算语义准确率，需要明确的参考标注；本实验没有准备标准答案，因此没有把人工观察转换成量化准确率。

## 八、Prompt 优化的影响

本次测试中，V1 和 V2 都能生成合法 JSON，因此改进 Prompt 没有提高 JSON 合法率或字段存在率。这个结果说明当前模型对基础结构要求已经有较好的遵循能力，但小样本和单次运行不足以证明两个版本的总体性能相同。

V2 的主要作用是澄清：

- 会议全称和简称的边界。
- 不同类型日期的归属。
- 主办单位的判断规则。
- 费用类别尽量保留原文语义。

从人工结果观察，V2 在通知 A 的完整会议名称和通知 C 的收费类别表述上更贴近原始材料。

## 九、当前局限

- 每个输入与每个 Prompt 只运行一次，没有统计模型输出波动。
- 三种输入规模较小，不能覆盖更多复杂格式。
- 没有标准答案，无法计算语义层面的字段准确率。
- 没有单独记录模型名称和请求耗时。
- 基础任务与 AIIoT 进阶任务已经使用独立模型；进阶任务增加了早鸟/普通收费阶段、优惠截止日期和注册政策字段。
- 空数组与 `null` 的业务语义仍可进一步统一。
- 截图由真实运行保存的结果文件渲染生成，并非对当时终端窗口的实时像素抓取。

## 十、改进方向

- 在相同模型和参数下增加重复运行次数，比较输出稳定性。
- 增加更多会议通知和缺字段格式。
- 为日期和费用增加更细的业务规则，例如收费阶段和对应截止日期。
- 保存模型名称、运行时间、耗时和请求状态等元数据。
- 如果以后引入明确的参考标注，再计算语义准确率；在此之前继续使用 JSON 合法率、字段存在率和人工错误分析。
- 继续扩展进阶模型，使其能适应更多收费阶段、币种和注册政策表达方式。

## 十一、结论

本次实验完成了三份会议通知的批量测试、JSON 结果保存、严格解析校验和运行结果截图。六次真实调用全部成功，并通过字段、日期和费用结构校验。通知 B 的未知信息保持为空，通知 C 的四类日期分类正确，说明 Prompt 和严格校验能够处理基础会议通知提取任务。

当前结果满足基础实验和 AIIoT 进阶多阶段收费任务的代码、Prompt、JSON 输出、严格校验和运行证据要求，但还不能据此证明语义准确率。
