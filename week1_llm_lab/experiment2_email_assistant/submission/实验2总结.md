# 实验2总结

## 1. 实验目标

使用大语言模型处理国际学术会议英文咨询邮件，完成意图识别、多问题提取、会议事实核验、人工审核判断和英文回复草稿生成。系统只生成草稿，不自动发送。

## 2. 实验数据与运行环境

- 会议：ICCBDA 2027。
- 基础邮件：A–F 共 6 封。
- 排除数据：G 为 AIIoT 2027 进阶邮件，不参与基础实验。
- 模型：`deepseek-chat`。
- 生成温度：0。
- 正式阶段：每封邮件依次执行分析、事实核验和回复生成，共 12 次阶段调用；自动校验重试 2 次，总计 14 次 API 调用尝试。
- 事实依据：仅允许使用 `data/iccbda_2027_fact_card.json`。

## 3. 处理方法

1. 从原始 txt 中提取主题、发件人和正文，形成结构化基础数据集。
2. 使用固定 9 类意图集合进行主意图和次级意图识别。
3. 提取全部明确问题以及论文标题、注册邮箱、费用陈述、付款陈述、服务请求和技术故障等实体。
4. 将每个问题独立对照事实卡，标记为 `supported`、`unknown`、`prohibited` 或 `actionable_without_fact`。
5. 根据事实核验结果生成英文草稿，并强制落实人工审核标记。
6. 使用独立验证脚本检查字段、问题覆盖、意图、审核一致性和事实约束。

## 4. 逐封结果

| 邮件 | 主意图 | 次级意图 | 问题数 | 人工审核 | 处理结果 |
|---|---|---:|---:|---|---|
| A | `registration_inquiry` | `submission_deadline` | 2 | 否 | 回答学生作者费用 USD 350 和截止日期 February 15, 2027 |
| B | `acceptance_inquiry` | 无 | 1 | 是 | 不披露个人录用结果，引导通过投稿系统查询 |
| C | `payment_inquiry` | 无 | 2 | 是 | 不确认付款状态；发票请求转人工 |
| D | `accommodation_inquiry` | 无 | 2 | 否 | 说明住宿尚未公布、交通信息未提供 |
| E | `payment_inquiry` | 无 | 2 | 是 | 不承诺退款资格或处理时限 |
| F | `technical_issue` | 无 | 1 | 否 | 要求错误截图、投稿编号、浏览器和文件信息 |

六封邮件的全部问题均已进入事实核验，问题总数为 10，事实核验条目总数为 10。

## 5. 事实控制结果

- 邮件 A 的两个问题均为事实卡支持项，可以直接回答。
- 邮件 B 的录用结果属于禁止直接回答事项，只能引导查询投稿系统。
- 邮件 C 的付款记录无法从事实卡确认，发票政策未提供，因此两项都必须人工审核。
- 邮件 D 的酒店和机场交通信息均未提供，草稿没有编造推荐、价格、班次或住宿安排。
- 邮件 E 的退款政策未提供，草稿没有承诺全额退款，也没有提供处理时限。
- 邮件 F 可以依靠标准故障信息收集流程处理，不需要虚构会议政策。

## 6. 实验中发现的问题及修正

1. 发票申请容易被模型当作独立意图。实验明确规定发票属于 `payment_inquiry` 下的具体问题，避免增加未定义的分类标签。
2. 首次运行邮件 C 时，分析结果没有标记人工审核，而事实核验判定需要审核。加入强制审核一致性校验后重新运行，最终分析、审计和回复三者一致。
3. 邮件 B 和 D 在首次分析中分别出现漏提问题和增加无依据次级意图，自动校验反馈后重试成功。
4. 将模型生成与事实放行拆成两个阶段，可以避免模型在同一阶段既生成答案又自我认定答案正确。

## 7. 实验结论

基础实验的六封邮件均完成结构化分析和英文草稿生成。系统能够正确处理多意图邮件、未知信息、付款争议、个人录用结果和退款等高风险场景。事实卡约束和确定性核验规则有效降低了编造会议政策的风险。

人工审核结果是 A、D、F 不要求审核，B、C、E 要求审核。所有输出均通过结构验证和事实核验覆盖检查。

## 8. 局限与改进方向

- 当前事实核验规则针对本次 6 封基础邮件设计，扩展到新场景时需要维护规则。
- 自动化流程没有执行真实人工审核，只负责生成标记和待审草稿。
- 后续进阶实验可继续比较单标签和多标签分类，并生成 Formal、Concise、Friendly 三种语气。
- 系统没有邮件发送接口，这是业务安全要求，而不是功能缺失。
